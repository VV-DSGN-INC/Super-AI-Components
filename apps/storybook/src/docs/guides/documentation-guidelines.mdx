# Documentation Guidelines

One rule generates everything on this page: **every fact about a component has exactly one home**,
and each documentation surface exists to hold a kind of fact no other surface can. When a fact
appears twice, one copy is already stale; it just has not been caught yet. The conventions are
`docs/design-system/component-build-brief.md` §Guidance and §Story, `story-conventions.md`, and the
citation gate's spec under `docs/superpowers/specs/`.

## The surfaces, and what each one holds

| Surface                                 | Holds                                                                                    | Never holds                                       |
| --------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `lib/catalog.manifest.ts`               | family, layer, declared `states` or `regions`, what it `consumes`                        | prose                                             |
| `<name>.docs.tsx`                       | the judgments: what it is, when to reach for it, dos and don'ts, accessibility, pitfalls | prop enumerations (the props table renders those) |
| `<Pascal>.stories.tsx`                  | one story per declared state, and the situations the component meets in a product        | a fourth copy of the variant list                 |
| The props table                         | the API surface, generated by react-docgen                                               | anything hand-typed                               |
| `component-specs.md` / `block-specs.md` | the requirements, normative including their prose                                        | implementation detail                             |

The test for a new story or paragraph: _is this fact already gated somewhere?_ A story that shows
`variant="secondary"` restates what the manifest, the docs page and the props table already hold. A
story that shows the component with a 90-character label is the only place that fact exists in the
repo.

## The docs module

`<name>.docs.tsx` exports a typed `ComponentDocs` object, and a Server Component reads it directly.
Two consequences have each broken the build: no `"use client"` in the module (its exports would
become opaque client references), and no JSX carrying event handlers (they cannot serialise across
the boundary). Interactive examples go in `<name>.examples.tsx`, marked `"use client"`, exporting
zero-prop named components.

Fill every field. `whyItMatters` cites the reference products the spec lists as evidence and never
invents one. `anatomy` names real `data-slot` values. `dos` and `donts` carry at least two entries
each, every one with a live example. `accessibility` has two required arms, both checked by the
contract gate:

- `keyboard`: the real tab-stop count and what changes it, which keys activate, and which keys a
  user will expect to work and **do not**.
- `screenReader`: the roles and `aria-*` actually present, how each accessible name is computed, and
  what silently degrades it.

Write it from the component's source, and record holes honestly. An unwritable `screenReader` note
is a finding about the component, not about the docs. One mechanical trap: `react/no-unescaped-entities`
is an error in this repo, so any literal quote or apostrophe in a JSX text node must be `&apos;` or
`&quot;`. It bites hardest in `.examples.tsx` files, where guidance prose quotes things.

## The citation gate

Prose may not cite what the component graph cannot reach. `check:contract` imports every docs module
and checks each backticked utility, slot or name in a claim-position field (`whatItIs`,
`whyItMatters`, `usage`, `anatomy[].note`, `dos[].text`, the two accessibility arms) against the
component's reachable source: its own files, what it `consumes`, and its vendored primitives, one
level deep. Anatomy slots are checked structurally, including template-literal prefixes such as
`approval-card-${verb}`. `donts` and `pitfalls` are exempt, because they cite what must not be
written; `aria-*` claims are deferred, because Base UI injects them at runtime and proving them is
story work. The first run raised 227 findings; three were genuine rot, prose that had outlived the
component, and the rest were gate work, triaged before green was believed.

## Stories are cases, not samples

Keep the scaffolded shape: `componentDocsPage(<Pascal>Docs)` as the docs page, one export per
declared state with real args, and no bare `Default` export. Blocks add `Empty` and `Responsive`,
which the gate enforces.

Then write the case stories. Name them exactly as below, so audit greps and rendered passes can find
them, and write only the ones that are **true for this component**: a story written to complete the
set reads as coverage and proves nothing.

| Story           | Write it when                          | What it must show                                                                                     |
| --------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `RTL`           | directional layout, icons or motion    | rendered under `dir="rtl"`, with chevrons, arrows and trailing slots mirrored                         |
| `ReducedMotion` | the component animates at all          | the `prefers-reduced-motion` branch, or its documented absence                                        |
| `KeyboardOrder` | it is focusable or contains focusables | the tab sequence, focus return on dismiss, and a visible focus treatment at every stop, play-asserted |
| `Controlled`    | it exposes a `value`/`onChange` pair   | driven by external state, play-asserted; without a play function this is a screenshot of a prop       |
| `EmptyLabel`    | any text slot is optional              | the no-label rendering, where icon-only tap targets usually fail                                      |
| `LongContent`   | any text slot is author-supplied       | about 90 characters, and the wrap, truncate or scroll decision the component actually makes           |
| `Mobile`        | always                                 | 375px, no horizontal scroll, inside a `w-[375px] max-w-full` wrapper                                  |
| `Boundary`      | a near-twin exists in the catalog      | the component beside its neighbours, with the choosing rule in the description                        |

Record the skipped ones in the block comment above the case-story block, one per line, in exactly
this grammar so a future gate can parse presence-or-annotated-absence:

```
 * // case-skip: RTL — no directional layout, icons or motion
```

Three rules bind every story:

- **The description carries the judgment.** A story with no description is a screenshot. Use a JSDoc
  block above the export; autodocs reads it.
- **No story introduces a value the component doesn't already use.** No new token, radius, size or
  colour; the 375px wrapper is the one sanctioned exception, because it is a test condition.
- **Demo content is honest.** Prompts, filenames, model names and error strings this system could
  really emit. No invented company names, no fabricated metrics, no lorem ipsum, and no
  every-variant-at-once grid, which markets the optionality this system exists to remove.

Play functions only where the component **owns** a behaviour: focus return, roving tabindex, escape
handling, distinct per-row accessible names. A play function that clicks a button and asserts the
button was clicked tests Storybook. And never assert behaviour you know to be wrong in order to get
green; a story that surfaces a defect is reported, not deleted.

## Four mechanical facts about this workbench

1. **Extra exports are legal.** `check:contract` asserts declared states ⊆ story exports, never the
   reverse, so case stories cannot break the gate and need no manifest entry.
2. **`Mobile` is wrapper-constrained, not `parameters.viewport`.** The runner behind
   `pnpm test:stories` has no Storybook manager, so a viewport parameter renders at desktop width in
   the run that gates. [Mobile viewport](?path=/story/foundations-mobile-viewport--home-shell)
   resizes the real browser instead.
3. **`ReducedMotion` documents a branch, or it documents its absence.** The runner emulates the
   preference for every test, so the story only differs from its neighbour if the component
   branches on the media feature. On a Base UI popup the guard has to restate the variant
   (`motion-reduce:data-open:animate-none`), or it loses the specificity tie and sits inert.
4. **Inside a Base UI portal you cannot read `document.activeElement` immediately after a tab.**
   The trailing focus guard redirects on a later frame. Settle with `waitFor` until focus is on an
   expected stop, seed the walk from where focus actually landed, then assert the cycle. `TaskTray`
   and `ShortcutsSheet` carry the idiom.

## Prose pages (Guides, Foundations, Content)

The pages in this workbench's rulebook are held to the same standard as the docs modules:

- Write from what the repo actually does, and cite the file, gate or decision that makes a claim
  true. A rule stated without its source becomes folklore.
- Every "don't" ships with its because.
- Where this library has no rule for a topic, say so. A gap stated is a backlog item; a gap filled
  with an invented rule is drift.
- Numbers are counted from the tree where the tree can be counted (`src/docs/_shared/system-counts.ts`)
  and dated where they cannot.
- The copy register follows the system's own content rules: name the object and the outcome, no
  marketing adjectives, no exclamation marks, no fabricated numbers.
- Pipe tables render because `remark-gfm` is wired into the MDX pipeline (`.storybook/main.ts`).
  Genuinely tabular facts may use them.
- Link to other pages with `?path=/docs/…`; the navigation stays inside the workbench.
